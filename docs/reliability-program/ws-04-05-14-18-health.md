### 2. Aggregation logic — verbatim (lines 136-144)

```python
red = any("looks_fresh_but_empty" in r for r in reasons)
if red:
    status = "RED"
elif reasons:
    status = "AMBER"
else:
    status = "GREEN"
    reasons.append("lab healthy: ran, populated, documented, no failing-OOS tactic surfaced")
```

- **GREEN** = `reasons` list empty when the chain is reached — a pure fallback, not a positive assertion.
- **AMBER** = `reasons` non-empty and none contains the literal substring `"looks_fresh_but_empty"`.
- **RED** = reachable from exactly **one** code path (lines 105-106: `status_val=="ok" and not rows`), plus two early AMBER returns (`lb is None` at 89-91; `status_val=="disabled"` at 95-97).
- **Severity ceiling bug:** `failing_oos`, `stale`, `insufficient_data`, `undocumented_tactics`, `factor_data_unavailable`, `stale_active_strategy_selection` can **never** escalate past AMBER, however many stack up — there is no severity counting, only a single hardcoded string gate for RED.

## WS14 — Regime coverage concentration

### 1. Computation and persistence chain

- Classifier: `watchlist_scanner/market_regime.py:27` `detect_market_regime()` → `{risk_on, risk_off, neutral, high_volatility}`.
- Recording: `watchlist_scanner/performance_feedback.py:56` `record_scan_signals()`, stamps `regime_label`/`regime_confidence`/`regime_data_quality` per row (lines 96-105), falling back to `"neutral"`/`0.0`/`"limited"` if the regime dict is empty (this fallback triple is the historic bug signature, see §4).
- Aggregation by regime (`performance_feedback.py:486-546`, `build_regime_performance_summary`):
```python
resolved_rows = [row for row in rows if row.get(primary_return_col) is not None]
regime_groups = {}
for row in resolved_rows:
    regime_groups.setdefault(str(row.get("regime_label") or "neutral"), []).append(row)
for regime_label, group in sorted(regime_groups.items()):
    by_regime[regime_label] = {"total_signals": len(group), "win_rate": ..., "avg_return_pct": ...}
```
- Persistence: `generate_regime_performance_reports()` (887-912) writes `outputs/regime/regime_performance.json` + `.md`.

### 2. Does any validity verdict account for concentration? — No

Grep-confirmed across `backtest_health.py`, `strategy_lab_health.py`, `quant_watch_probes.py`, `semantic_liveness.py`:
- `backtest_health.py:100-104` has a "regime" check but reads a **different** artifact (`poc_simulation_results.json` → `added_metrics.per_regime`) and only flags `degenerate_regimes` when **all** buckets are `"unknown"` — not a concentration measure.
- `strategy_lab_health.py` — zero reference to `regime_performance` at all.
- `quant_watch_probes.py` — no automated regime-concentration probe; the only related entry, `manual:regime_classifier_neutral_collapse`, is a hand-maintained ledger row, not code.
- `tools/policy_recommender.py:611-624` (`_recommendation_data_quality`) checks per-regime sample sufficiency (`regime_sample >= 3` → `"performance_backed"`) but **treats a large single-regime sample as increasing confidence**, never penalizing that ~99% of evidence sits in one bucket. This tool has **zero production callers** (unwired CLI tooling).
- `quant_feedback.py`'s `by_regime` (different source: `decision_context_log.jsonl` × `decision_outcomes.jsonl`) is consumed only for GUI/memo reporting (`daily_run_status.py:571-579` surfaces presence/`evidence_status`/`fallback_rate`, no concentration logic).

**Conclusion:** `regime_performance.json` (and `quant_feedback.json`'s `by_regime`) is purely observational — never gates a GREEN/AMBER/RED verdict or discounts a gauge/tactic's claimed edge for regime concentration.

### 4. Existing degeneracy guard — catches plumbing, not distribution skew

Fix: commit `077c8a1a` ("correct producer ordering that collapsed signal_outcomes to constant neutral"), documented in `docs/REGIME_CLASSIFIER_NEUTRAL_COLLAPSE.md`. Root cause: `watchlist_scanner/__main__.py` called the feedback cycle before `detect_market_regime()` was attached, so every row got the fallback triple `(neutral, 0.0, limited)`.

Guard, two parts:
1. `portfolio_automation/semantic_liveness.py:143-150` — `detect_single_value_collapse(regimes, probe="regime_label", min_sample=30, allowed_single_values={"neutral", ""})`. Fires **only** when the entire column is a single distinct value **not** in the allowlist. `"neutral"` is explicitly whitelisted, so **a 100%-neutral column never triggers this check** — designed to be silent on exactly this concentration pattern.
2. `.claude/commands/daily-tool-analysis.md:98,273,380` — checks `len(by_regime)==1 AND resolved_signals>=30` combined with `avg_regime_confidence==0.0` (the fallback signature) as the smoking gun; explicitly distinguishes this from "a legitimately calm single-regime window ... confidence ~0.77–0.88" which is "report, don't alert."

**Would it catch today's 98.8%-neutral situation? No**, for two independent reasons: (1) it requires exactly **one** distinct label; today's file has **two** (`neutral` + `high_volatility`), so the trigger condition doesn't fire at all. (2) Even hypothetically at 100%, the guard explicitly passes any non-zero `avg_regime_confidence` through as "legitimately calm" — and today's `neutral.avg_regime_confidence = 0.327`, `high_volatility.avg_regime_confidence = 0.83` (both real, non-zero), so neither would trip the `==0.0` condition regardless.

**Bottom line:** the fix and its guard answer "is the classifier/producer wired correctly" (plumbing-integrity), not "is the resulting label distribution so skewed that an aggregate win-rate/return is really just one regime's performance wearing an all-regime label" (statistical-validity/overfitting). `docs/REGIME_CLASSIFIER_NEUTRAL_COLLAPSE.md`'s own acceptance criterion is satisfied by "more than one legitimate regime label present" — no threshold on how mass is split between them. No code path anywhere computes "share of total resolved evidence per regime" and gates a verdict on it.

## Cross-cutting synthesis

- All four workstreams converge on the same structural pattern: **every current health verdict in this repo is a single collapsed status (GREEN/AMBER/RED) computed as "no enumerated bad thing detected,"** not as a positive/statistical claim of validity. None of the 5 surveyed artifacts (WS18) separate operational vs data vs statistical vs governance dimensions into distinct sub-verdicts; where multiple arrays exist (`daily_run_status.stages/artifacts/content_liveness`), they are computed but folded into one `overall_status` via simple counting, and count omissions (the `"unknown"` stage bucket) silently favor GREEN.
- WS4's `still_works_oos is False` bug and WS14's regime-concentration gap are the same root defect at different layers: **"was not observed to fail" is treated as "was validated as correct."** Neither the strategy-lab assessor nor any regime/gauge-validity path currently distinguishes "never tested" from "tested and passed," or "edge measured across diverse conditions" from "edge measured almost entirely in one condition."
- WS5's finding is the governance-side counterpart: the human-approval and sandbox-scoping controls around active-strategy selection are real and correctly gated (confirmed), but the system has **no mechanism to even surface**, let alone gate on, a persistent divergence between a human-approved artifact and the deterministic ranking that nominally justifies it — and the candidate universe (8 fixed profiles) structurally excludes the tactic that would resolve the divergence if approved.
- WS18's consumer-contract findings (daily-tool-analysis.md) constrain any redesign: `strategy_lab_health` and `backtest_health` are not read directly by the daily skill (owned by weekly/pattern-loop skills respectively), so a schema change to either has a narrower blast radius than a change to `daily_run_status.json` or `artifact_registry_status.json`, which are read-first and field-referenced by name in ~5 of the ~32 heartbeat lines with an explicit AMBER-cap-on-missing/stale rule.

No implementation is proposed per audit instructions.
